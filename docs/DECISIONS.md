# Product and implementation decisions

- Registration requires a password of at least 12 characters, matching the documented administrator setup policy. The DTO enforces this for self-service registration.
- Money continues to use Prisma `Decimal` columns (`Decimal(12,2)`); amounts are not represented as floating point.
- Prisma and SQL retain camelCase `businessId`; no `business_id` mapping is used.
- Booking stays are calendar dates stored as PostgreSQL `DATE` (Prisma `DateTime @db.Date`) and use half-open `[checkIn, checkOut)` ranges so same-day turnover is allowed. Checkout must follow check-in. `CANCELLED` and `NO_SHOW` records do not block rooms; all other statuses block. A room in `MAINTENANCE` is out of service and cannot be booked or checked into; current `OCCUPIED`/`CLEANING` status does not prevent a future reservation because date availability is enforced by the exclusion constraint.
- Stay totals are room `Decimal(12,2)` rates multiplied by the number of calendar nights using Prisma Decimal arithmetic. Client totals are never accepted. Booking status changes use the explicit state machine and check-in/out change room status in the same transaction.
- `NO_SHOW` is added in its own migration because PostgreSQL will not allow a newly added enum value to be used by another statement in the same migration transaction. The following hand-written migration uses `btree_gist` and a partial GiST exclusion constraint as the authoritative concurrency-safe overlap check; Prisma does not model that exclusion constraint, while schema diff still verifies represented schema changes.
- `ActivityLog.businessId` is nullable because historical events for users with multiple memberships cannot be reliably assigned to a business without action context. The migration backfills users with exactly one membership and only adds `NOT NULL` when a nonempty table has no remaining nulls. The activity list endpoint filters by the authenticated business; null/global events are not returned in tenant lists.
- Several tenant models have no independent CRUD API: `CatalogCategory` is currently an unused legacy model, `BusinessMember` is created by onboarding, `SaleItem` is nested in sales, and `StockMovement` is exposed only as product history. Cross-tenant tests exercise their parent/list surfaces where available and the schema guard requires each model to remain accounted for.
- Booking totals are a snapshot of the room rate at creation. A deliberate room or stay-date edit reprices the entire stay using the room's current Decimal rate; later room-rate edits do not rewrite existing bookings.
- Invoice totals originate from a booking and payments are recorded in a ledger. Invoice paid amount and balance are calculated from its total and booking payments in one shared Decimal helper; the stored amountPaid/balance columns are maintained only as compatibility snapshots and cannot be edited through generic routes. Voiding is allowed only before any payment is recorded.
- Editing dates or room reprices an unpaid invoice in the same transaction as its booking. Once any payment is recorded, a change that would alter the invoice total is rejected; changing guest/source data remains allowed.
- Sales use the same Decimal financial calculation and reject zero/over-total or invalid partial tenders. The retail model stores a single initial tender on Sale and has no payment ledger or later-sale-payment API; changing it to incremental payments requires a separate model migration, so booking invoice payments remain ledger-based.
- Dashboard date-only occupancy and front-desk dates use Africa/Lagos calendar dates. Occupied rooms are rooms with CHECKED_IN stays covering the selected date; reserved rooms are PENDING/CONFIRMED stays covering it. A checkout date is exclusive, allowing turnover on that date. Maintenance rooms are excluded from bookable room totals.
- Retail Sale stores its initial tender and uses the same Decimal amount/status derivation helper for validation and dashboard outstanding totals. It does not support incremental sale payments because the current Sale schema has no payment ledger or record-payment API; booking payments remain ledger-based.
- API monetary values are Prisma Decimal/string values. Browser totals use integer minor-unit arithmetic only for display and pre-submit previews; no JavaScript floating-point arithmetic is used for money. BigInt support requires the web TypeScript target to be ES2020.
